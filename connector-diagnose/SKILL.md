# 连接器诊断修复


## 概述

诊断连接器（MCP Server）连接失败：分析根因 → 评估可自动修复 → 询问用户 → 执行修复 → 验证结果，循环直至解决或转手动修复方案。

## 诊断上下文格式

用户从连接器卡片跳转对话时，消息中包含以下结构化诊断上下文：

```
连接器「{名称}」连接失败，请使用 connector-diagnose 技能帮我诊断原因并给出修复方案。

当前状态：failed / disconnected
错误信息：{Kernel 透传的 error 字符串}
错误类别：{config_error / environment_missing / network_timeout / process_crash / auth_failure / unknown}
连接日志路径：{logPath}（可能为空）
详细原因：{errorCause}（可能为空）
后端建议：{suggestedSolution}（可能为空，仅作参考）

配置项检查：
- {KEY}: 已填写（长度 N 字符） / 未填写

MCP Server 配置摘要：
- command: {脱敏后的命令}
- environment keys: {env key 列表，不含值}

运行环境检测：
- 操作系统: {windows / macos / linux}
- 架构: {x64 / arm64}
- 终端: {powershell / zsh / bash}
- 运行时命令检测:
  - {command}: {可用 / 不可用}（{版本}）[{来源}]
  - ...

本地诊断建议：{checkConfig / checkEnvironment / checkNetwork / checkProcess / aiDeepAnalysis}
```

`运行环境检测` 段是安装运行时的关键依据：据此选择当前系统对应的安装命令；若相关命令标记为"不可用"，进入 Step 4.3 安装运行时。

## 完整诊断-修复-验证流程

```
Step 1: 根因分析
    ↓
Step 2: 评估可自动修复性
    ├── 可自动修复 → Step 3: 询问用户
    │       ├── 用户同意 → Step 4: 执行修复
    │       │       └── Step 5: 验证修复结果
    │       │           ├── 连接成功 → 输出成功报告，结束
    │       │           └── 仍然失败 → 回到 Step 1（最多 3 轮）
    │       └── 用户拒绝 → Step 6: 输出手动修复方案
    └── 不可自动修复 → Step 6: 输出手动修复方案
```

### Step 1：根因分析

根据诊断上下文的 `错误类别` 确定首要排查方向：

| 错误类别 | 首要排查方向 |
|---------|------------|
| `auth_failure` | Token 是否过期、权限范围是否足够、格式是否正确 |
| `environment_missing` | Node.js/Python 是否安装、版本是否兼容、PATH 是否正确 |
| `network_timeout` | API Host 是否可达、防火墙/代理是否拦截、DNS 是否正常 |
| `process_crash` | 入口文件是否存在、依赖包是否安装、JS 运行时错误 |
| `config_error` | 配置值格式、占位符、JSON 格式是否有效 |
| `unknown` | 综合分析，逐一排查以上方向 |

同时检查：
1. 逐项检查 `配置项检查` 中每个 KEY：长度为 0 或明显过短（< 4 字符）视为未填写/异常
2. 根据 `command` 首词判断运行时（node/npx/python/uvx），对照 `运行环境检测` 段确认是否缺失
3. **读取 [references/known-failures.md](references/known-failures.md)** 的「连接器特定指南」，按连接器名称快速匹配已知故障模式
4. **优先读取 `连接日志路径` 指向的日志文件**：根因的第一手证据（**优先级高于 `错误类别` 与 `错误信息`**）
   - 读取文件末尾 50 行，或搜索 `error`、`failed`、`closed`、`initialize` 等关键字，提取具体失败原因
   - **以日志中的实际错误为准**：若日志根因与 `错误类别` 指向的排查方向矛盾，以日志为准
   - `错误信息`/`详细原因` 仅作摘要参考，`后端建议` 仅作参考不盲从
   - 日志可能含敏感信息：**不输出日志原文**，仅引用关键错误行
   - 日志文件不存在或不可读时，说明"日志不可读"，退回基于摘要的分析

### Step 2：评估可自动修复性

| 修复类型 | 可自动修复 | 示例 |
|---------|-----------|------|
| 配置项缺失或格式错误 | ✅ 是 | 修改 `mcp_settings.json` 中的值 |
| 占位符未替换 | ✅ 是 | 将 `<GITCODE_TOKEN>` 替换为实际值 |
| npm 依赖缺失 | ✅ 是 | 在 MCP Server 目录执行 `npm install` |
| Playwright 浏览器未安装 | ✅ 是 | 执行 `npx playwright install` |
| Node.js / Python / uv 未安装 | ✅ 是 | 全局安装（winget/brew/apt/官方脚本/内网镜像），失败转手动修复方案（见 Step 4.3） |
| Token 过期或权限不足 | ❌ 否 | 需用户登录第三方平台获取新 Token |
| 网络不可达 / VPN 未连接 | ❌ 否 | 需用户手动检查网络环境 |
| Chrome 扩展未安装 | ❌ 否 | 需用户在浏览器中手动安装 |

判断标准：AI 能通过文件操作或 Shell 命令直接解决的问题为可自动修复。运行时安装由 AI 直接执行，**不限制安装手段**（允许 `sudo`/管理员权限、允许修改系统 PATH），以成功安装依赖环境为唯一目标；仅在命令执行失败时才转手动修复方案。

### Step 3：询问用户是否自动修复

可自动修复时，必须向用户确认后再执行：

```
## 诊断结果

**连接器：** {名称}
**错误类别：** {类别中文名}
**严重程度：** 🔴 严重 / 🟡 警告

### 原因分析
{1-2 句话说明最可能的失败原因}

### 可自动修复
{是的，可以自动修复} —— {说明将执行的操作}

**是否需要我自动执行以下修复操作？**
1. {操作 1 描述}
2. {操作 2 描述}

> 请回复"是"或"否"。自动修复涉及修改连接器配置文件及必要的系统级操作（如安装缺失的运行时，可能需要管理员权限），均会在上一步列明。
```

约束：
- 必须列出所有将执行的操作，让用户知道具体改什么
- 必须等待用户明确回复"是"后才能执行，禁止先斩后奏
- 用户回复"否"时，直接跳到 Step 6 输出手动修复方案

### Step 4：执行修复

用户同意后，按列出的操作依次执行。

**4.1 修改配置文件**：
- 定位 `mcp_settings.json`（路径：`%USERPROFILE%\.codeartswork\mcp\mcp_settings.json`），修改对应连接器的 `environment` 字段值，修改后读取文件确认写入成功
- 若配置项不全或需编辑完整 JSON：引导用户使用应用内"自定义连接器"弹框（详见 references「通过自定义连接器弹框修改配置」）

**4.2 安装依赖**：
- 对 MCP Server 目录执行 `npm install`（如果 package.json 存在）
- 对 Playwright 执行 `npx playwright install`
- 执行前先检查是否已安装，避免重复

**4.3 安装运行时（Node.js / Python / uv）**：

当错误类别为 `environment_missing`，且 `command` 首词为 `node`/`npx`/`python`/`python3`/`uvx`/`uv` 时，运行时未安装。**AI 直接全局安装**。

> ⚠️ **执行前必须读取 [references/known-failures.md](references/known-failures.md) 的「运行时自动安装矩阵」**，其中包含各 OS 的完整安装命令、华为内网镜像下载地址、全局安装脚本与手动兜底步骤。严格按该矩阵执行，禁止凭记忆猜测安装命令。

按矩阵执行时遵循以下要点：
1. **二次确认**：执行前先 `node --version` / `python --version` / `uv --version`，确认确实缺失（检测结果可能滞后）
2. **执行前确认**：列出将执行的安装命令，遵循 Step 3 询问机制（已在 Step 3 确认的不再重复询问）
3. **执行**：每条命令前说明"正在执行：{命令}"（允许 `sudo` / 管理员权限）
4. **验证**：执行 `<command> --version` 确认输出版本号，并用 `where <command>`（Win）/ `which <command>`（macOS/Linux）确认可被找到；两者都通过才算安装成功
5. **失败必须回显**：命令失败时输出**完整错误输出（stdout/stderr）**，据此判断失败原因（权限/UAC、网络超时、HTTP 404、依赖缺失）后切换下一方式；禁止静默重试同一命令
6. **无法执行命令时**：转 Step 6 输出手动修复方案，**同时提供命令行方案与图形化方案**两种方式（见 Step 6）
7. **下载源首选**：内网环境（公司网络）**直接首选华为内网镜像**（公共源必然失败，不必先试再切）；公共源仅在无内网镜像时使用
8. **标记重启需求**：本轮若安装了运行时或修改了系统 PATH，标记为"需重启验证"（Step 5 据此提示重启）

安装完成后引导用户回到连接器页面重新启用/诊断（进入 Step 5）。

**4.4 安装约束**：
- 若 `sudo` 需交互密码且无法输入，转 Step 6 手动修复方案
- 其余（不限制手段、失败回显、双方式手动输出）见 4.3 要点与 Step 6

### Step 5：验证修复结果

修复完成后，**不要自行安排连接验证任务、不要发起连接测试或等待 Kernel 自动验证**（自动验证耗时长，会让用户空等）。改为引导用户查看连接状态，按本轮修复类型分两种情况：

**情况 A：本轮涉及安装运行时 / 修改系统 PATH**（CodeArtsWork 进程的环境变量是启动时快照，PATH 变更不重启不生效）

```
修复已完成。但本次安装/PATH 变更需重启 CodeArtsWork 才能生效：
1. 完全退出 CodeArtsWork（含系统托盘图标，确保进程结束）
2. 重新打开 CodeArtsWork
3. 到"我安装的连接器"页面查看「{名称}」状态：
   - 🟢 绿色"已连接" = 修复成功，可正常使用
   - 🔴 红色"异常诊断" = 仍未修复，点击"智能诊断"重新诊断，我会继续分析
```

**情况 B：本轮仅为配置/依赖类修复**（如修改 mcp_settings.json、npm install、playwright install）

```
修复已完成。请到"我安装的连接器"页面查看「{名称}」的连接状态：
- 🟢 绿色"已连接" = 修复成功，可正常使用
- 🔴 红色"异常诊断" = 仍未修复，点击"智能诊断"重新诊断，我会基于新的错误信息继续分析
```

仍然失败时：用户重新触发"智能诊断"会带来新的诊断上下文（含最新错误与日志路径）→ 回到 Step 1 重新分析根因 → **排除已尝试方案**（记录每轮修复操作，不重复同一修复）→ 最多循环 3 轮，超过后建议"卸载重装"。

第 3 轮仍然失败时输出：
```
已尝试 3 轮自动修复均未成功。

建议您尝试以下兜底方案：
1. 卸载该连接器后重新安装
2. 检查 CodeArtsWork 应用日志中是否有更详细的错误信息
3. 联系连接器提供方确认兼容性
```

### Step 6：输出手动修复方案

对于不可自动修复的问题，或用户拒绝自动修复 / AI 无法执行命令时，输出面向电脑小白的详细手动修复方案。

**核心原则：目标用户是电脑小白，不会用命令行、不知道什么是环境变量。每一步必须写到"点哪个按钮、在哪个页面、应该看到什么"的粒度。**

**安装软件时同时给出两种方式**：涉及安装 Node.js/Python/uv 时，手动方案必须**同时**提供：
- **方式一：命令行方案**——用户在终端可粘贴执行的完整命令（如 `irm https://astral.sh/uv/install.ps1 | iex`、`winget install OpenJS.NodeJS.LTS`），含重新加载 PATH 与验证命令（已验证可执行通过）。**多条命令必须逐条分步返回**：每条命令一个编号步骤，并明确提示"粘贴一条、回车执行、看到结果后再粘贴下一条"，禁止把多行命令一次性返回
- **方式二：图形化方案**——"打开浏览器 → 下载安装包 → 双击安装 → 跟随向导 → 验证"的鼠标操作步骤（官网或华为内网镜像 → 点击下载 → 双击安装包 → 勾选/下一步 → 完成 → 回到应用验证）。涉及配置系统路径时注册到**系统变量（Machine）**而非仅用户变量

两种方式并列输出，用户任选其一。具体安装步骤参考 references 的「运行时自动安装矩阵」之"兜底手动指导"。

写作规范：
1. 每一步必须编号，不跳跃步骤
2. 给出确切网址（完整 URL），不写"去官网"模糊指引
3. 用引号标注界面元素名称（点击"下一步"、"Install Now"）
4. 每步后加"你应该看到..."描述预期界面
5. 用 ⚠️ 标注常见坑（如"必须勾选 Add python.exe to PATH"）
6. 避免技术术语（不说"PATH 环境变量"，说"让系统能找到 Node.js 程序"）
7. Windows 专属指引写"按 `Win + R` 键"等具体操作
8. 每段外部操作结束后写"回到 CodeArtsWork 应用"并指引页面位置
9. 方案最后必须有"修复后验证"小节
10. **双方式输出**：安装软件的手动步骤必须同时给出"命令行方案"（终端粘贴执行的完整命令）与"图形化方案"（浏览器下载→双击安装→向导），用户可任选其一
11. **手动安装步骤优先参考 [references/known-failures.md](references/known-failures.md)** 的步骤模板（Node.js 安装指南、Python 兜底、uv 命令行+图形化步骤、连接器特定指南）

模板格式：

```
## 诊断结果

**连接器：** {名称}
**错误类别：** {类别中文名}
**严重程度：** 🔴 严重 / 🟡 警告

### 原因分析
{1-2 句话}

### 手动修复步骤

**方式一：命令行安装（可粘贴执行，已验证通过）**

> ⚠️ 以下命令请**逐条**复制到终端：每粘贴一条按一次回车，看到上一条执行完成后，再粘贴下一条。不要一次粘贴多行。

1. 打开终端：按 `Win + R` 键，输入 `powershell`，回车
2. 粘贴执行第 1 条命令（安装）：{完整安装命令}
   - 你应该看到：{命令执行输出}
3. 上一条执行完成后，粘贴执行第 2 条命令（重载环境变量）：{命令}
4. 最后粘贴执行验证命令：`{command} --version`，你应该看到版本号

**方式二：图形化安装（浏览器下载 / 安装向导）**

1. 打开浏览器，访问 {确切 URL}
   - 你应该看到：{描述页面内容}
2. {下载/安装操作，图形化}
   - ⚠️ {常见坑提醒}
   - 你应该看到：{描述成功后界面}
3. {回到 CodeArtsWork 应用，填入配置}
   - 你应该看到：{弹出"更新成功"提示}

### 修复后验证

1. 在连接器页面找到「{名称}」卡片，打开开关
2. 等待 5-10 秒，观察状态指示灯：🟢 绿色 = 成功；🔴 红色 = 仍失败，请点击"诊断"发给我新错误
```

## 约束

- **用户确认**：所有自动修复操作必须经用户明确同意后执行（见 Step 3）
- **透明性**：执行前列出操作，执行中说明进度
- **安装手段**：不限制（允许 `sudo`/管理员/修改系统 PATH），以成功安装为唯一目标（见 Step 4.3/4.4）
- **循环限制**：最多 3 轮，每轮记录已尝试方案避免重复，超过建议卸载重装
- **脱敏**：Token/密钥等敏感信息只显示前后各 4 字符
- **诚实性**：信息不足时说明"信息不足"，不猜测
- **兜底**：`unknown` 类别或 3 轮失败 → 卸载重装
- **手动方案**：面向电脑小白，命令行+图形化双方式输出（见 Step 6）
