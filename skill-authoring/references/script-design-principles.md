# Skill 脚本设计原则
> 目标：让 Skill 在提示词、工具与脚本之间做正确取舍。脚本不是默认答案；只有在确定性、复现性、批处理或工程可靠性明显受益时才使用。
## 1. 核心原则
1. **Agent 负责判断与创造**：理解、建议、审美、设计、思考、反思、创意、灵感等开放任务，不用脚本限制。
2. **工具优先**：已有可靠工具/CLI 能完成确定性操作时，直接调用，不重复造轮子。
3. **确定性任务用脚本**：固定算法、严格格式、大批量处理、精确校验、复杂文件/API 操作优先脚本。
4. **复杂任务优先组合**：Agent 做判断与创造，脚本做数据准备、执行、校验和批处理。
5. **标准库优先**：能不用第三方依赖就不用。
6. **脚本必须可独立运行、可诊断、可测试、路径无关。**
## 2. 先判断：要不要脚本？
### 不用脚本
以下任务通常直接写在 `SKILL.md`：
- 建议、方案比较、策略思考
- 审美判断、设计方向、创意与灵感
- 批评、反思、推理、开放式分析
- 写作、改写、总结、解释、报告撰写
- 需要结合语境、权衡取舍或生成新想法的任务
- 一次性、低风险且 Agent 可直接完成的操作
  判断标准：**任务价值主要来自理解、判断、创造或表达，而不是机械复现时，优先 Agent。**
### 应该用脚本
满足任一条件时优先考虑脚本：
- 输出必须确定、可复现
- 有复杂计算、排序、匹配、解析或校验
- 批量处理大量文件/记录
- 需要精确读写文件格式
- 调用 API，并涉及分页、重试、签名或结构化响应处理
- 多步骤重复执行，遗漏一步就会出错
- 输入输出需要机器校验
- 失败必须给出明确错误与退出码
  判断标准：**这一步失败会破坏后续流程，而且不希望 Agent 自由发挥时，用脚本。**
## 3. 什么时候 Agent + 脚本结合？
复杂 Skill 默认优先这种方式。
### Agent 负责
- 理解用户意图与上下文
- 提供建议、判断与取舍
- 审美、设计、创意、灵感生成
- 思考、反思、批评与综合推理
- 选择工具/脚本并构造参数
- 解释、复核并二次加工结果
### 脚本负责
- 数据准备与精确计算
- 批量处理和固定转换
- 文件解析/生成
- 数据校验与规则检查
- API 调用与分页/重试
- 可机器验证的约束
### 推荐流程
```text
用户请求
→ Agent 理解、思考并确定方案
→ 必要时调用工具/脚本准备数据或执行确定步骤
→ Agent 基于结果继续判断、设计或创作
→ 脚本按需做最终校验/批处理
```
### 避免
- 用脚本代替建议、审美、设计、创意或反思
- 用固定分数/规则冒充开放式判断
- 用 Agent 手工模拟复杂算法或批量机械操作
- 每一步都包成脚本，或让 Agent 与脚本重复同一逻辑
## 4. 用什么脚本？
### Shell
适合：
- 文件移动、复制、查找
- 简单文本处理
- 调用已有 CLI
- 串联少量命令
  常用：`grep`、`sed`、`awk`、`find`、`xargs`。
  不适合：复杂 JSON、复杂分支、复杂错误处理、强跨平台需求。
### Node.js
适合：
- JSON 处理
- REST API / `fetch`
- 文件与目录操作
- Web 数据转换
- JavaScript 生态工具链
  优先使用标准库与内置 `fetch`。

### Python
适合：
- 数据分析/科学计算
- 表格处理
- 图片处理
- PDF 生成/解析
- Python 生态明显更成熟的任务
  不要因为习惯 Python 就默认所有脚本都用 Python。

### 浏览器 JavaScript
网页任务优先在浏览器上下文执行 JS：
- DOM 提取
- computedStyle
- 页面元素交互
- 页面内状态/数据读取
  除非环境明确要求，否则不要用 Python 再包装浏览器操作。

## 5. 语言选择速查
| 场景 | 推荐 |
|---|---|
| 建议/审美/设计/创意/反思 | Agent |
| 简单文件/命令串联 | Shell |
| JSON/API/Web 数据 | Node.js |
| DOM/页面交互 | 浏览器 JS |
| 数据分析/表格 | Python |
| 图片/PDF | Python |
| 已有 CLI | 直接调用 CLI |
| 语义判断 + 确定执行 | Agent + 脚本 |
如果多个方案都能完成，按以下优先级选择：
1. 环境已有运行时/工具
2. 标准库即可完成
3. 依赖最少
4. 最容易测试和维护

## 6. 脚本职责边界
一个脚本尽量只负责一类确定性任务，例如：
```text
scripts/
├── parse_input.py
├── validate_data.py
├── transform_data.mjs
└── export_result.py
```
不要创建巨型 `do_everything.py`。
脚本间只是简单顺序调用时，由 Skill 工作流协调即可；只有 orchestration 本身复杂时才增加总控脚本。
也不要过度拆分：只使用一次、逻辑很短、与主流程高度耦合的代码可留在当前脚本中。

## 7. 输入与参数规范
脚本应：
- 必要参数显式传入
- 参数名表达真实语义
- 合理默认值只用于真正可选项
- 枚举参数限制合法值
- 支持 `--help`
- 输入非法时立即失败
  推荐：
```bash
python export.py --input data.json --format csv --output result.csv
```
避免依赖难理解的位置参数：
```bash
python export.py a b 1
```

## 8. 路径规范
脚本必须基于**自身文件位置**解析 Skill 内资源。
禁止：
- 依赖 cwd 的 `./data/...`
- `os.chdir()` / `process.chdir()`
  原则：
- Skill 内资源：相对脚本自身位置解析
- 用户输入：通过参数传入
- 输出位置：参数指定或使用明确默认位置
- 从任意目录调用都应正常工作

## 9. 编码与跨平台
- 文本统一 UTF-8
- Python 文件读写显式 `encoding="utf-8"`
- 不依赖系统默认编码
- 不硬编码平台路径分隔符
- 使用语言自带路径库
- 不假设固定操作系统或固定 cwd

## 10. 输出规范
当输出会被 Agent 或程序继续处理时，优先 JSON。
`stdout`：
- 最终数据
- 结构化结果
  `stderr`：
- 进度
- 警告
- 错误
- 调试信息
  推荐：
```json
{"status":"success","data":{}}
```
不要把进度文本混入 JSON 输出。

## 11. 错误处理
禁止吞异常。
失败时必须：
1. 明确哪一步失败
2. 给出可操作的错误原因
3. 使用非零退出码
4. 不把半成品伪装成成功结果
   错误信息应让 Agent 能区分：
- 参数错误
- 文件不存在
- 格式非法
- 依赖缺失
- API 失败
- 权限不足
  可恢复错误可有限重试；不可恢复错误尽快失败。

## 12. 依赖规范
优先级：
```text
标准库 > 已有工具/CLI > 已安装依赖 > 新增第三方依赖
```
新增依赖前确认：
- 标准库是否已经够用
- 环境是否已有等价能力
- 是否值得增加安装成本
- 是否降低可移植性
  必须新增时：
- Python：`requirements.txt`
- Node.js：`package.json`
- Shell：说明依赖的 CLI
  不要在正常执行路径中临时 `pip install` / `npm install`，除非 Skill 明确规定。

## 13. API 与外部系统
调用 API 时应：
- 设置明确超时
- 校验 HTTP 状态和响应结构
- 对分页显式处理
- 重试仅用于可恢复错误，并限制次数
- 不把 Token/密钥硬编码在脚本中
- 凭证使用环境变量或运行环境提供
- 错误中避免泄露敏感信息
  Agent 负责选择请求目标与参数，脚本负责稳定执行与校验。

## 14. 文件写入与副作用
涉及写入、删除、覆盖、上传、发送等操作时：
- 明确目标路径/对象
- 默认避免破坏性覆盖
- 写前检查目标状态
- 删除范围最小化
- 高风险操作优先支持 `--dry-run`
- 需要原子写入时先写临时文件再替换
- 不静默修改与任务无关的文件

## 15. 可测试性
关键脚本应可独立运行。
至少验证：
- 正常输入
- 缺少参数
- 非法输入
- 文件不存在
- 从不同 cwd 调用
- 输出格式符合约定
- 失败时退出码非零
- 高风险操作的 dry-run 不产生副作用
  复杂逻辑尽量拆成纯函数，便于单元测试。

## 16. 何时复用脚本，何时直接写新逻辑？
优先复用已有脚本，当：
- 输入输出契约一致
- 逻辑本质相同
- 只需要参数变化
  可以新增脚本，当：
- 任务职责不同
- 原脚本继续加分支会变得难维护
- 新任务依赖不同生态或运行时
  不要为了复用而把一个简单脚本改造成充满模式开关的万能脚本。

## 17. 推荐决策树
```text
1. 核心价值是否来自理解、建议、审美、设计、创造、思考或反思？
   → 是：Agent 主导；需要数据准备/校验时再结合脚本
2. 已有工具/CLI 能直接完成确定性操作吗？
   → 能：直接调用
3. 是否需要批量、复杂算法、精确 I/O、固定转换或严格校验？
   → 否：继续用 Agent
   → 是：使用脚本
4. 网页 DOM/页面状态？ → 浏览器 JS
5. JSON/API/Web 数据？ → 优先 Node.js
6. 数据分析/表格/图片/PDF？ → 优先 Python
7. 简单文件/命令串联？ → Shell
8. 同时有开放判断与确定执行？ → Agent + 脚本
```

## 18. 最终检查清单
- [ ] 这个步骤真的需要脚本？
- [ ] 已有工具是否能直接完成？
- [ ] 创造性/审美/建议/反思是否保留给 Agent？
- [ ] Agent 与脚本职责是否清楚且不重复？
- [ ] 语言/运行时是否是最简单合适的选择？
- [ ] 是否优先标准库？
- [ ] 路径是否完全不依赖 cwd？
- [ ] 是否避免 `chdir`？
- [ ] 文本是否统一 UTF-8？
- [ ] 参数是否明确、可校验？
- [ ] 数据输出是否结构化？
- [ ] 进度/错误是否走 stderr？
- [ ] 失败是否返回非零退出码？
- [ ] 是否没有吞异常？
- [ ] 外部依赖是否已声明？
- [ ] 凭证是否没有硬编码？
- [ ] 高风险写操作是否有保护？
- [ ] 脚本能否从任意目录独立运行？
- [ ] 是否覆盖关键失败场景测试？

## 一句话原则
> **让 Agent 负责理解、判断与创造，让工具负责现成能力，让脚本负责确定性执行与校验；不要用脚本把本应开放思考的部分写死。**
