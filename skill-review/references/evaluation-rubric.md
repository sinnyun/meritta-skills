# Evaluation Rubric

总分 100 分。

| 维度 | 分值 | 说明 |
|------|------|------|
| Intent & Requirement Fidelity | 15 | 是否理解了正确的用户意图，完整满足核心需求 |
| Capability Authenticity | 20 | 声称的能力是否真实存在，Claim 与实际实现边界是否一致 |
| Evidence & Test Validity | 15 | 证据是否可信，测试是否真正证明核心能力 |
| Real-world Robustness | 15 | 离开 Demo 环境后是否还能工作 |
| Product / Human Sanity | 15 | 结果是否符合人类常识和产品价值 |
| Dependency & Environment Fitness | 10 | 依赖和目标环境是否真实匹配 |
| Operational & Maintainability | 5 | 性能、成本、延迟是否合理，是否易于维护 |
| Structure / Context Efficiency | 5 | 目录结构和 Context 是否高效 |

---

## Intent & Requirement Fidelity（15 分）

判断：我们实现的是不是用户真正需要的东西？

| 分数区间 | 标准 |
|----------|------|
| 13-15 | 完整满足需求，理解了用户真实意图和隐含需求。没有"技术正确但解决了错误问题"。 |
| 10-12 | 核心能力完整，存在少量边界问题。部分次要需求未覆盖。 |
| 6-9 | 只能覆盖部分核心需求。关键功能缺失或理解偏差。只机械实现了字面表达。 |
| 0-5 | 明显偏离原始需求。Skill 做的事和用户想要的不是一回事。 |

---

## Capability Authenticity（20 分）

判断：Skill 声称拥有的每一个核心能力，是否真的存在？

| 分数区间 | 标准 |
|----------|------|
| 17-20 | 所有核心能力均有真实工具、数据或用户输入支撑。Claim 与实际能力边界一致。Remove-the-Mock Test 通过。 |
| 13-16 | 核心能力基本成立，但部分边界能力只有弱证据。Claim 基本准确。 |
| 8-12 | 存在能力声明大于实际实现的问题。部分能力依赖 Mock / Fabricated Data。 |
| 0-7 | 核心能力主要依赖 Mock / Fabricated Data，实际无法完成用户任务。Claim 严重膨胀。 |

---

## Evidence & Test Validity（15 分）

判断：证据是否可信？测试是否真正证明了核心能力？

| 分数区间 | 标准 |
|----------|------|
| 13-15 | 证据来自真实 Tool / API / 运行结果。Test Oracle 可靠。测试验证真正的用户目标，不只是内部函数。有独立验证。 |
| 9-12 | 主要证据可信，部分测试只验证 Happy Path。Test Oracle 基本可靠但不够全面。 |
| 4-8 | 测试主要由 Creator 自行构造，Test Oracle 可能有效也可能无效。测试只证明内部函数工作。 |
| 0-3 | 测试只是验证 Creator 自己的假设。Creator-Test Collusion。测试 PASS 不代表能力成立。 |

---

## Real-world Robustness（15 分）

判断：Skill 离开 Demo 环境以后还能不能工作？

| 分数区间 | 标准 |
|----------|------|
| 13-15 | 处理真实自然语言输入、不完整输入、模糊输入。规模变化不会导致失败。依赖失败有合理降级。 |
| 9-12 | 主要场景可以工作，部分 Edge Case 失败。规模变化时有基本处理。 |
| 4-8 | Happy Path Overfit。只处理理想结构化输入。真实规模下可能失败。 |
| 0-3 | 只在 Demo 环境工作。真实输入 / 真实规模 / 环境变化都会导致失败。 |

---

## Product / Human Sanity（15 分）

判断：结果是否符合人类常识和产品价值？

| 分数区间 | 标准 |
|----------|------|
| 13-15 | 输出结果对真实用户有用且合理。没有技术上成立但现实中荒谬的行为。人类专家愿意交付。 |
| 9-12 | 结果基本合理，个别场景可能不够理想。遗漏了部分人类专家会考虑的因素。 |
| 4-8 | 存在明显不合理的结果。技术上正确但产品上不够好。用户可能需要额外处理才能使用。 |
| 0-3 | 结果明显荒谬或对用户具有误导性。人类专家不会交付。 |

---

## Dependency & Environment Fitness（10 分）

判断：Skill 的目标运行环境是否真的具备它依赖的能力？

| 分数区间 | 标准 |
|----------|------|
| 9-10 | 所有依赖在目标环境中真实可用。环境要求清晰声明。依赖问题已主动解决或合理降级。 |
| 7-8 | 主要依赖可用，部分依赖未验证。环境要求基本清晰。 |
| 3-6 | 存在环境假设但未验证。部分依赖在目标环境可能不存在。 |
| 0-2 | 依赖不存在的 Tool / API / Credential。Creator 环境有但目标环境没有。 |

---

## Operational & Maintainability（5 分）

判断：实现是否以合理的成本和延迟完成任务？是否易于维护？

| 分数区间 | 标准 |
|----------|------|
| 5 | 性能、成本、延迟合理。结构清晰，命名规范，易于维护。 |
| 4 | 基本合理，有少量优化空间。可维护性良好。 |
| 2-3 | 性能或成本可能不合理。可维护性一般。 |
| 0-1 | 成本/延迟严重不合理。难以维护。 |

---

## Structure / Context Efficiency（5 分）

判断：目录结构和 Context 是否高效？复杂度是否匹配问题？

| 分数区间 | 标准 |
|----------|------|
| 5 | 目录结构合理。SKILL.md 精简。复杂度与问题复杂度匹配（不 Overengineering 也不 Underengineering）。 |
| 4 | 基本合理，有少量冗余或不足。 |
| 2-3 | 结构不合理。过度设计或设计不足。 |
| 0-1 | 严重失衡。完全没有必要的复杂度，或严重不足。 |
